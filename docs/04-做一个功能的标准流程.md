# 做一个功能的标准流程

这是本项目唯一的功能交付节奏。七个步骤按顺序做，每一步都可以停下来问对方；不要跳过第 2 步和第 5 步。

## 1. 先确认规则，再动手

打开 `业务规则基线.md`，找到这个功能对应的编号（例如预约改期是 R07，二维码有效期是 R09）。
基线里写“用户已确认”的按规则实现；写“Demo 工程默认”的按文档口径实现并在代码注释里标注是默认值。
基线没有写清楚的，先在群里问一句，不要自己发明规则。

同时确认这个功能属于谁：见 `双人协作分工.md` 的责任表。共享模块只有一个负责人，另一个人评审。

## 2. 先改契约，再改代码

在 `contracts/openapi.yaml` 里增加或修改路径、字段、错误码，并在 `contracts/examples/` 补一个真实样例。
契约是两个人的共同资产：改契约要提出来让对方确认，不要一边写代码一边偷偷改字段名。
字段一律 `snake_case`，枚举一律大写字符串，时间一律带时区，ID 一律不透明字符串。

## 3. 开一条短分支

```bash
git switch main
git switch -c feat/reservation-unlimited-edit
```

分支名用 `feat/`、`fix/`、`test/`、`docs/` 开头，后面是模块和能力，用小写字母加连字符。
分支只活几天，功能确认完就合并回 `main`，不要开长期个人分支，最后靠拼接。

## 4. 先写会失败的测试，再写实现

后端每个功能至少覆盖三类情况：

- 时间边界：窗口端点内、端点上、端点后；跨过 00:00 与 06:00。
- 权限：正确角色通过，其他角色 403，前端绕过直接调接口也要 403。
- 并发与重复：同一请求重放两次，业务结果只能有一份。

前端至少保证 `npm run build` 通过（里面包含类型检查）。
测试跑不过就是没做完，不要用「先注释掉」的方式通过检查。

## 5. 本地自检

```bash
cd apps/api && ./.venv/Scripts/python.exe -m pytest -q
cd ../web && npm run build
```

涉及数据库的，还要跑：

```bash
cd apps/api && ./.venv/Scripts/python.exe -m alembic upgrade head
```

三项全绿才进入下一步。绿了以后在群里说一句话：改了哪个能力、跑了哪些检查。

## 6. 一次功能一次提交

先看带了什么文件，再提交：

```bash
git status
git add apps/api/app/modules/reservation contracts/openapi.yaml
git commit
```

提交信息格式与检查项见 `05-Git提交与分支.md`。
`git status` 里出现 `.env`、密钥、真实学生数据、`node_modules`、`dist`、`.venv` 时立即停下，这些不该进仓库。

## 7. 交给对方合并

功能确认后把分支推给对方看的远程（配置好之前，直接把改动说明发给对方），请对方 review。
跨模块事务、授权、通行和日期规则必须对方看过才能合并。
合并后自己再跑一次第 5 步，确认主干是干净的。

## 什么叫「完成」

契约、实现、迁移、测试、文档更新五项都在同一次提交里，且第 5 步三项检查通过。
只有页面能点开不算完成；只有接口能返回也不算完成。
