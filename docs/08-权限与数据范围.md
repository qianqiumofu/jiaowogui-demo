# 权限与数据范围

原则一句话：**权限和范围都在后端判定，前端隐藏入口只是体验**。直接拿别的角色令牌调接口必须被拒绝，这是每次联调都要验的事。

## 现有底座

- `apps/api/app/modules/identity/schemas.py`：`Role`、`SessionContext`、`Person`。
- `apps/api/app/modules/authorization/policies.py`：动作到角色映射 `ACTIONS`，`is_allowed(...)`。
- `apps/api/app/modules/authorization/dependencies.py`：`require(action)` 依赖与范围缺失时的 403。
- 会话与范围解析：`apps/api/app/modules/identity/service.py` 的 `SessionStore` 与 `resolve_scope(...)`。
- 动作清单：`policies.ACTIONS`，新增动作必须同时写测试。
- 会话：模拟统一身份登录后签发，切角色会轮换会话并让旧令牌失效。

## 两类账号来源（R18、R19）

| 来源 | 谁用 | 登录 | 权限怎么来 | 通知渠道 |
| --- | --- | --- | --- | --- |
| `UNIFIED_SCHOOL` | 学生、辅导员、园区使用者 | 学校统一身份账户，带校内邮箱 | 目录关系授予，一人可多角色 | 邮箱（报告和预警邮件） |
| `STAFF_LOCAL` | 宿管（阿姨，雇佣人员） | 园区在本系统内统一注册、分发的独立账号 | 园区在创建账号时指定固定管理楼栋；改绑、重置口令、停用同样只由园区执行 | 站内待办，无邮箱不生成邮件 |

要点三条：

1. 统一账户正式版应当由服务端自动识别身份并直接进入对应工作台。Demo 阶段先用登录页选择账号、`/auth/role-switch` 轮换角色代替，这条差异登记在 `13-待确认事项.md`，接入统一身份时必须补齐，不得当成已完成。
2. 宿管不属于校内人员，不出现在统一身份目录里；工号账号是本系统自建的工作账号，与统一账户同存 `users` 表、靠 `source='STAFF_LOCAL'` 区分，`login_name` 与校内工号无关且全局唯一。
3. 权限只由园区端授予：`staff_account:*` 动作仅 `CAMPUS` 角色可调用，宿管之间、辅导员和学生对账号表都没有入口。楼栋范围仍由后端 `resolve_scope` 判定，前端隐藏入口不算权限。

## 通知的收件边界（R15、R16）

| 动作 | 学生 | 辅导员 | 宿管 | 园区 | 说明 |
| --- | --- | --- | --- | --- | --- |
| `notification:read` | 无 | 有 | 有 | 有 | 只读自己的收件箱；`/notifications{,/{id}}` 一律按 `recipient_user_id` 过滤，别人的通知返回 404 |
| `notification:mark_read` | 无 | 有 | 有 | 有 | 只能标记自己的通知为已读，同样走 404 过滤 |
| `notification:dispatch` | 无 | 无 | 无 | 有 | 演示用的手动投递入口，只在 M1 联调阶段开放 |
| `notification_job:read` | 无 | 无 | 无 | 有 | 查看任务队列状态与失败原因 |

三条不能靠前端实现的边界：

1. 模板与收件人角色不匹配直接 422 `NOTIFICATION_TEMPLATE_MISMATCH`，名单不能发给辅导员，日报不能发给宿管。
2. 风险跟进提示的收件人出现园区角色时 403 `NOTIFICATION_RECIPIENT_FORBIDDEN`，园区不收件（R16）。
3. 读取自己的收件箱用 `require_own_resource`，不走数据范围解析：没有固定管理且不在有效代班窗口时范围为空、
   会被判 `SCOPE_UNRESOLVED`，但那不能让他看不到自己的通知。

## 三个必须满足的判定顺序

1. 令牌有效（否则 401 `UNAUTHENTICATED`）。
2. 当前角色被授予该动作（否则 403 `FORBIDDEN_ACTION`）。
3. 结果集被 scope 限制（宿舍、负责学生、本人），范围缺失时 403 `SCOPE_UNRESOLVED`，不返回全量；
   指定了具体资源但不在范围内时 403 `OUT_OF_SCOPE`，`details.allowed` 回显当前范围。

## 角色能看什么

| 角色 | 范围 | 备注 |
| --- | --- | --- |
| 学生 | 只有本人 | 不能自行改归属楼栋 |
| 辅导员 | 只负责学生 | 负责关系由 B 的目录同步；缺失记配置异常 |
| 宿管 | 只有效值班楼栋 | 读范围由 `directory.get_duty_buildings` 现算 = 名册固定值守 ∪ 当夜代班 ∪ 园区建号时绑的楼栋；固定值守那一栋**按业务夜整段生效**（白天与 06:00 交班后照样打得开今晚名单），代班只在自己那段班次区间内生效。范围全空时 403 `SCOPE_UNRESOLVED`，不返回全量 |
| 园区 | 全校授权范围 | 主动查询预警，不接收风险推送 |

### 名册范围与当前授权

- 统一业务权限继续通过 `require(action)` 与 `SessionContext.scope` 校验。
- 今晚名单、补录、风险列表与处置沿用名册固定值守、账号绑楼与当前有效代班的并集。固定名册按业务夜日期生效，代班按绝对班次窗口生效。
- `fixed_watch_buildings` / `get_fixed_watch_staff` 只提供名册事实查询，不作为风险的独立权限来源；风险收件人继续用 `get_duty_staff` 并在投递时重新校验。

原始原因文本、联系方式、导出字段另设字段级权限，不能用角色一刀切放开。

## 联系方式怎么发

- 名单接口 `GET /buildings/{id}/tonight` **不返回** `phone`；阿姨在名单里点「联系」才走
  `GET /directory/students/{id}/contact`（动作 `contact:read_duty`，仅宿管）。
- 该端点先按有效值班楼栋校验，不在范围与学生不存在给同一个 `OUT_OF_SCOPE`，避免探测名册。
- 24:00 汇总后的异动推送是**唯一**在名单之外携带联系方式的通道：收件人由
  `directory.get_duty_staff(building_id, at)` 现算，只可能是当班人员，不允许扩到园区（R16）。

## 值班授权只能由园区端写入

- 每栋楼夜间的值班阿姨是**固定**的，长期关系登记在 `building_duty_roster`（迁移 0022）：
  园区写 `POST /duty-roster`（动作 `duty:assign`），同一人员同一楼栋登记更新同一行，换人须卸任原人员并登记新人员；卸任走 `POST /duty-roster/revoke`，
  要 `building_id` + `staff_user_id`，那栋楼没有固定负责人时 404 `DUTY_ROSTER_NOT_FOUND`。
- 固定班**不限制「一栋只有一位」**：一栋可以并排白班（06:00—18:00）与夜班（18:00—次日 06:00）两位，
  一人也可以主值多栋；`shift_start/shift_end` 是每晚重复的时刻，跨零点由读取侧按业务夜回绕判定。
- 逐夜授权因此只剩**代班**这一种：`POST /duty-assignments` 与 `POST /duty-assignments/switch`
  （动作同为 `duty:switch`）写的是 `duty_assignments` 里 `is_substitute=true` 的行，只在那一夜的班次窗口内生效；
  `DELETE /duty-assignments/{duty_id}` 撤销。无需先拥有固定主值；一栋多人、一人多栋，重复同人同楼同夜同开始时刻返回 409 `DUTY_SLOT_TAKEN`。
- 阿姨端没有自助授权：`duty:switch` 不含 `DORM_MANAGER`，宿管与辅导员只有 `duty:read`，
  而且读到的行强制收窄到本人（自己的名册与自己的代班）。
- 名册卸任会顺带解掉园区建号时绑的那一栋（`users.building_ids`），否则「名册删了人、她照样进得来今晚名单」；
  这一处调用身份领域服务 `staff_accounts.remove_building_binding`，与名册撤权、审计共用事务，失败全部回滚。
- 每次名册与代班写入都会把该楼栋那一夜的 24:00 汇总排进 `background_jobs`（幂等键
  `DORM_TONIGHT_SNAPSHOT:<楼栋>:<业务夜>`），园区端那份带负责人姓名的晚归单就是这么来的；
  快照里的负责人在 24:00 冻结，之后换人不改历史。

## 园区统计与导出的边界

- 动作：`statistics:read`（`GET /statistics`）、`campus:query`（`GET /statistics/filters`）、
  `export:create`（`POST /exports` 与本人任务的查询/下载），三者都只授予 `CAMPUS`；其余角色直接调一律 403。
- 园区是**全校范围**读，因此这里没有「按 scope 收窄」这一层，靠的是口径本身：统计读模型只出聚合数，
  联系方式与学生身份天然不在返回体里（R11）。
- 导出是「谁发起谁可下载」：`requested_by` 不等于当前用户时给 404 `EXPORT_NOT_FOUND`，
  不区分「不存在」与「不属于你」，避免探测别人的导出行为。
- 导出只接受统计读模型那 10 个口径参数，未知键创建即 422；范围不能通过导出悄悄变宽。
- 保留期（`EXPORT_RETENTION_DAYS`，默认 7 天）到点清空 CSV 正文、保留任务行做审计，下载改判 410。
  清空是立即提交的，不因随后抛出的 410 回滚。

## 风险投递的硬边界

风险事件的收件人只能是负责辅导员与当班宿管。任何新增的通知任务在投递前都要二次校验收件人范围，
**园区角色不得出现在风险收件人里**，这条要写成测试。

- 风险收件人与可见范围沿用当前基线：负责辅导员与当班宿管，固定名册、账号绑楼及有效代班均参与范围计算。
- 负责辅导员、思政教师与宿管沿用接手、追加跟进和办结流程；园区与学院负责人只读，校级无风险处理权限。
- 不得因为超时或未确认返宿生成风险事件、通知或提醒任务（R15）。

## 门禁终端不是会话用户

`POST /device/scan` 用设备身份认证：请求头 `x-device-id` + `x-device-token`，服务端只存 sha256 摘要，
匹配不到就是 401 `DEVICE_UNKNOWN` / `DEVICE_UNAUTHORIZED`。学生令牌调它一律无效，反过来设备凭据
也拿不到名单或返宿记录——那两页仍走会话与动作判定（`building:tonight`、`return:read_scoped`、
`manual_return:create`）。

终端只报告「这枚码在本门点被刷了」，放行与否、当夜名额是否已占用，全部由服务端按
`pass_codes` 与 `return_records` 判定；客户端传来的任何状态都不参与授权计算。
返宿记录页按角色收窄：辅导员只回负责学生，宿管只回有效值班楼栋，园区与学生拿不到该接口（403）。

## 加新接口时的做法

```python
@router.get("/buildings/{building_id}/tonight")
def tonight(
    building_id: str,
    context: Annotated[SessionContext, Depends(require("building:tonight"))],
) -> dict: ...
```

在 `resolve_scope()` 里补上该角色的数据边界，再在 `tests/test_identity_scope.py` 加一条越权断言。
前端可以调 `/authz/actions` 决定导航项是否显示，但不能代替后端判断。
