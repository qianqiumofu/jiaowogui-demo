## 固定 ID 约定

ID 是不透明字符串，但演示数据必须固定，否则两人的测试对不上。

| 类型 | 前缀 | 示例 |
| --- | --- | --- |
| 用户 | `usr_synth_` | `usr_synth_0002` |
| 学生 | `stu_synth_` | `stu_synth_0001` |
| 学院 | `org_college_` | `org_college_cs` |
| 园区 | `campus_park_` | `campus_park_east` |
| 楼栋 | `bldg_` | `bldg_a1` |
| 门点 | `gate_` | `gate_a1_north` |
| 设备 | `dev_synth_` | `dev_synth_a1_01` |
| 预约 | `res_synth_` | `res_synth_0001` |
| 通行码 | `pass_synth_` | `pass_synth_0001` |
| 归返聚合 | `ret_synth_` | `ret_synth_0001` |
| 风险事件 | `risk_synth_` | `risk_synth_0001` |
| 宿管工号账号 | `usr_staff_` | `usr_staff_a2_01` |
| 通知（邮件/待办） | `ntf_synth_` | `ntf_synth_0001` |

表中带 `_synth_` 的是种子数据的固定 ID，两人测试互相对齐用。服务端运行时新建的记录不承诺固定值，
用短前缀加随机后缀：预约 `resv_`、预约修订 `rev_`、工号账号 `usr_staff_`、任务 `job_`、通知 `ntf_`。

学生编号段：`stu_synth_0001`—`0012` 属于 `bldg_a1`，`0013`—`0024` 属于 `bldg_a2`。
李辅导员负责 `0001`—`0006`；王宿管当晚值班 `bldg_a1`，`23:00` 后代班含 `bldg_a2`。
`stu_synth_0009` 是李辅导员本人的学生身份，用于多角色演示。

改这些约定要走一次单独的提交，并同时更新双方受影响的测试。

## 通知链路演示口径

收件人 ID 就是上表的 `usr_synth_000X`：`0001` 学生、`0002` 李辅导员、`0003` 王宿管、`0004` 赵园区。
园区端「演示投递」页面直接选人，`GET /api/v1/auth/demo-accounts` 会带上 `user_id`。

能演示的四类正文与它们的边界：

| 模板 | 收件角色 | 正文要点 |
| --- | --- | --- |
| `NIGHT_ROSTER` | 当班宿管 | 23:30 汇总名单；写明「23:30 不是申请截止时间」，投递时刻重新取数，反映最新改期 |
| `DAILY_REPORT` | 负责辅导员 | 前一业务夜名单；固定带一句未确认返宿不等于证明未归，不催办（R15） |
| `WEEKLY_REPORT` | 负责辅导员 | 七个业务夜的按夜计数，取消不计 |
| `RISK_ALERT` | 辅导员 + 当班宿管 | 按配置的演示阈值逐人一条；园区投给自己会被 403 拒绝（R16） |

`campus` 投给 `usr_synth_0004` 的任何 `RISK_ALERT` 都会被拒绝，这是演示里最容易被追问的一条，
不要用「前端不显示」代替。工号账号 `dorm` 没有邮箱，同一事件只落站内待办，正文结尾换成
「本条为站内待办，无需回复。」

投递入队后要跑一次 worker 才会出现在收件箱，见 `01-运行手册.md` 的 worker 一节。
