# 数据库与迁移

数据库是 PostgreSQL 17，唯一一套。本地用 `docker compose up -d postgres` 起，不用 SQLite 替代并发测试。

## 迁移规则

1. 迁移文件由模块负责人编写，B 负责统一合并，保证只有**一个迁移头**。
2. 已经应用到别人库里的迁移**不重写**，只能追加新迁移修正。
3. 每个迁移只做一件事，`upgrade()` 与 `downgrade()` 都要能跑。
4. 加列给默认值、加索引、加唯一约束分属不同迁移，方便回滚。

## 常用命令

```bash
# 升级到最新（可重复运行）
cd "F:/A_homework/交我归/apps/api"
./.venv/Scripts/python.exe -m alembic upgrade head

# 查看当前版本
./.venv/Scripts/python.exe -m alembic current

# 自动草案（必须先写好 SQLAlchemy 模型，并确认生成的语句）
./.venv/Scripts/python.exe -m alembic revision --autogenerate -m "add reservations"

# 手写迁移（推荐用于加唯一约束、锁语义和视图）
./.venv/Scripts/python.exe -m alembic revision -m "add night_returns unique"
```

`alembic/env.py` 的 `target_metadata` 目前是 `None`。B 建好 `app/db/` 模型后改成 `Base.metadata`，
A 写预约模型时追加自己的表到同一个 `Base`。

## 已有的硬约束

- `reservations(student_id, service_date)` 唯一：一晚一条预约。
- 归返聚合 `night_returns(student_id, service_date)` 唯一：一晚一次返宿。
- 一条归返可以关联多条证据 `return_evidence`，统计返宿次数用归返聚合，不用证据条数。
- 业务写入与 `outbox_events` 同事务提交，消费者按 `event_id` 去重。
- 修改接口带 `expected_version`，版本过期返回 409。
- 锁顺序统一：归返聚合 → 预约 → 通行码/尝试；事务内重新检查状态和版本。

## B 已落地的表名与迁移头（2026-11-17）

上面的概念名与实际实现有一处对应关系，请按实际名写代码：

| 概念 | 实际表 / 约束 | 迁移 |
| --- | --- | --- |
| 归返聚合 `night_returns` | `return_records`，唯一约束 `uq_return_per_night(student_id, service_date)` | `0007` |
| 证据 `return_evidence` | `return_records.evidence` JSONB + `idempotency_key` 唯一 | `0007`（Demo 单表，真实证据分级时再拆表） |
| 通行码 | `pass_codes`，部分唯一索引 `uq_one_active_pass_per_reservation(reservation_id) WHERE status='ISSUED'` | `0007` |
| 园区受控导出 `export_jobs` | `export_jobs`，`idempotency_key` 唯一；口径存在 `params` JSONB，CSV 正文在保留期内存 `csv_content` | `0009` |

- **迁移号已分配**：`0001`—`0009` 全部由 B 落地，当前头是 `0009`；**A 的 `reservations` / 核验 / 通知表请用 `0010`**（`down_revision = "0009"`）。两人各开一个同号迁移会形成两个 head，`upgrade head` 直接失败。
- `pass_codes.reservation_id`、`verification_id` 故意**不建外键**：A 的表晚点落地，B 只按不透明 ID 读写。
- `devices.token_digest`（`0007` 加列并回填）是终端身份摘要，明文派生公式见 `docs/10`。
- 已应用到库的迁移不重写，需要改字段请另开一号。
