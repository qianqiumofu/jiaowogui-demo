# 数据库与迁移

数据库是 PostgreSQL 17，唯一一套。本地用 `docker compose up -d postgres` 起，不用 SQLite 替代并发测试。

## 迁移规则

1. 迁移文件由模块负责人编写，B 负责统一合并，保证只有**一个迁移头**。
2. 已经应用到别人库里的迁移**不重写**，只能追加新迁移修正。
3. 每个迁移只做一件事，`upgrade()` 与 `downgrade()` 都要能跑。
4. 加列给默认值、加索引、加唯一约束分属不同迁移，方便回滚。

## 常用命令

```bash
# 升级到最新（可重复运行）
cd "F:/A_homework/交我归/apps/api"
./.venv/Scripts/python.exe -m alembic upgrade head

# 查看当前版本
./.venv/Scripts/python.exe -m alembic current

# 自动草案（必须先写好 SQLAlchemy 模型，并确认生成的语句）
./.venv/Scripts/python.exe -m alembic revision --autogenerate -m "add reservations"

# 手写迁移（推荐用于加唯一约束、锁语义和视图）
./.venv/Scripts/python.exe -m alembic revision -m "add night_returns unique"
```

`alembic/env.py` 的 `target_metadata` 是 `app.db.Base.metadata`。全仓库只有一份表定义
（`app/db/models.py`），要加表就在同一个 `Base` 上追加，不得再开第二个模型文件或第二个 `Base`。

## 已有的硬约束

- `reservations(student_id, service_date)` 唯一：一晚一条预约。
- 归返聚合 `night_returns(student_id, service_date)` 唯一：一晚一次返宿。
- 原规划的一条归返多条独立证据 `return_evidence` 尚未完整落地；当前证据为 return_records.evidence JSONB。统计返宿次数用正式返宿记录，不用证据条数。
- 当前预约变更与持久化通知事件同事务提交；通用 `outbox_events` / `inbox_events` 尚未完整落地，不能冒充已有表。
- `background_jobs.business_key` 全表唯一（键里已带任务类型前缀）：同一（模板 + 业务夜 + 收件人集合）
  重复入队只有一条；已完成后再投递走 `:r1`、`:r2` 重放槽位，进行中的任务不产生第二条。
- `notifications(recipient_user_id, business_key)` 唯一：重试同一个任务不会给同一收件人重复落信。
- `users.login_name` 唯一，统一账户与工号账号同表同命名空间（`0013` 起）；工号账号靠 `source='STAFF_LOCAL'`
  区分，带 Demo 明文 `password` 与 `building_ids`，不写 `email`。
- 修改接口带 `expected_version`，版本过期返回 409。
- 锁顺序统一：归返聚合 → 预约 → 通行码/尝试；事务内重新检查状态和版本。

## 实际落地的表名与迁移头（2026-11-18，合并 B 侧交付后）

上面的概念名与实际实现有一处对应关系，请按实际名写代码：

| 概念 | 实际表 / 约束 | 迁移 |
| --- | --- | --- |
| 归返聚合 `night_returns` | `return_records`，唯一约束 `uq_return_per_night(student_id, service_date)` | `b0007` |
| 证据 `return_evidence` | `return_records.evidence` JSONB + `idempotency_key` 唯一 | `b0007`（Demo 单表，真实证据分级时再拆表） |
| 通行码 | `pass_codes`，部分唯一索引 `uq_one_active_pass_per_reservation(reservation_id) WHERE status='ISSUED'` | `b0007` |
| 园区受控导出 `export_jobs` | `export_jobs`，`idempotency_key` 唯一；口径存在 `params` JSONB，CSV 正文在保留期内存 `csv_content` | `b0009` |
| 预约 | `reservations`（唯一 `(student_id, service_date)`）+ 只追加的 `reservation_revisions` 改期历史 | `0001` |
| 模拟收件箱 | `notifications`，唯一 `(recipient_user_id, business_key)`，`job_id` 外键指向 `background_jobs.id` | `0003` |
| 工号账号 | 已并入 `users`，靠 `source='STAFF_LOCAL'` 区分 | `0002` 建表、`0013` 搬数据后删除 |

- **迁移号现状（2026-11-18 整合）**：保留 A 已提交的 `0001→0002→0003` 原文；B 的首次导入迁移以 `b0001→…→b0009` 追加，其 `b0005` 复用已有共享任务表；再接 `0013`（账号搬入 users，保留时间与字段容量）、`0014`（宿管异动通知模板）、`0015`（账号字段容量对齐）。当时单头为 `0015`。没有重编号 A 已应用迁移。
- **单头现状（2026-11-20）**：`0022_building_duty_roster`（楼栋固定值班名册，B 落）。
  A 的下一号请用 `down_revision = "0022"` 的 **`0023`**，单头仍由 B 统一合并。
  `0022` 的 `upgrade()` 里有一条**不可逆**的 `DELETE FROM duty_assignments WHERE NOT is_substitute`
  （逐夜主值改由名册现算），`downgrade()` 只还原表结构、拿不回那些行；已应用不重写。
  旧库（11-18 之前的独立演示库）不要直接 `upgrade` 或 `stamp`，重建请用 `app/db/seed.py` 与 `app/db/experience.py`。
- B 独立旧库的 `0001—0009` 与 A 的同号历史不是一回事，**不能直接 stamp 或直接 upgrade**。本轮支持并测试空库与 A 原 `0003` 库升级；B 旧库的数据迁入需要另做备份、识别及迁移方案，不在未知历史的库上猜测。
- `tests/test_migration_integration.py` 在真实 PG 临时 schema 验证空库、A 旧头升级、旧工号账号的 ID/登录名/展示名上限、时间戳保留与回退再升级。
- `pass_codes.reservation_id`、`verification_id` 与 `reservations.student_id` 故意**不建外键**：双方只按不透明 ID 读写，加载顺序与将来分库都不受影响。
- `devices.token_digest`（`0007` 加列并回填）是终端身份摘要，明文派生公式见 `docs/10`。
- 已应用到库的迁移不重写，需要改字段请另开一号。
