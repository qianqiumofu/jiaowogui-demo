# 今晚名单交接（B → A）

2026-11-16 两次改口径：① 汇总时刻 23:30 → **24:00**，该时刻是**该业务夜**的首次申请截止；
② 截止跟着「预约所属业务夜」走，**次夜申请不受当夜截止影响**，且 24:00 要主动给阿姨推一条「已汇总共 N 人」。
2026-11-17 再加口径 ③④：③ 00:00–06:00 的二维码通行要同步进阿姨的汇总单，**通行本身不推送**；
④ 今晚名单严格只覆盖当前业务夜，06:00 一到自动切次夜，前一晚的通行与领码情况到「返宿记录」页按业务夜查。
本文只登记 B 已经实现、等 A 对接的部分；规则本身以 `业务规则基线.md` v1.3 为准。

## 1. B 需要 A 提供的唯一函数

```python
# apps/api/app/modules/reservation/service.py
def list_for_building(building_id: str, service_date: date) -> list[dict]: ...
```

- 返回该楼栋该业务夜**全部预约**，含已撤销的（阿姨要看到【撤销】异动，不能消失）。
- **只给 `service_date` 等于入参那一夜的预约**。B 侧读到越夜或缺 `service_date` 的行会直接丢弃（名单只含当夜是硬要求），所以越夜数据在阿姨端是看不见的，别指望 B 帮你兜。
- 不做权限判断：调用方已确认 `building_id` 在当班范围内，这里不要再按角色过滤。
- 未实现时 B 侧返回 501 `NOT_IMPLEMENTED`，`details.capability = "reservation.list_for_building"`；
  落地后 `apps/api/app/modules/building_list/source.py` 不用改，直接生效。

字段（B 只读这些，缺字段会 500，请一并给出）：

| 字段 | 类型 | B 的用途 |
| --- | --- | --- |
| `student_id` | str | 与目录住宿做连接，名单的主键 |
| `service_date` | str，`YYYY-MM-DD` | 当夜校验：不等于所查业务夜的行不进名单（需求 ③） |
| `planned_return_at` | str，带 +08:00 的 ISO | 显示晚归时间；与汇总基准比较判断是否【改期】 |
| `status` | str，`ACTIVE / CANCELLED / FULFILLED / CLOSED` | `CANCELLED` 且基准里不是 → 标【撤销】 |
| `version` | int | 推送去重键的一部分 |
| `updated_at` | str，带时区 ISO | 异动发生时间 |

`planned_return_at` 请统一用业务时区偏移（`+08:00`），不要给 UTC 或裸时间。

## 2. 预约异动要推给当班宿管（需求 ①③）

B 已经写好装配与收件人解析，A 在**预约通过 / 改期成功 / 撤销成功**的事务提交后各调一次：

```python
from app.modules.building_list import notify

notify.push(
    {
        "student_id": "stu_synth_0001",
        "building_id": "bldg_a1",           # 目录缺失时兜底用，正常由 B 覆盖
        "change_kind": "APPROVED",           # APPROVED / RESCHEDULED / CANCELLED
        "planned_return_at": "2026-11-17T00:40:00+08:00",
        "reservation_version": 2,
    },
    clock.now(),
)
```

- `notify.push` 自己算收件人：`directory.get_duty_staff(building_id, at)`，只有此刻在班的人收到；
  无人在班时收件人为空，**不降级成群发**，也不得改成园区（R16）。
- 消息内容已含楼栋寝室号、联系方式、学院、学号、晚归时间（需求 ①）；改期与撤销只发短句（需求 ③）。
- 去重键：`dorm:{building_id}:{student_id}:{change_kind}:{version}`，重试请复用同一个键。
- 发送走 A 的 `notification.enqueue_building_message(template, recipient_ids, payload, dedup_key)`；
  模板名 B 侧固定为 `dorm.reservation.approved / .rescheduled / .cancelled`。
  `enqueue` 未实现时 B 抛 501，`details.capability = "notification.enqueue_building_message"`。
- 推送失败不能回滚预约事务：请 `try/except` 后记日志，别把申请本身带失败。

### 24:00 汇总完成那条（需求 ②）B 已经接好，只等 `enqueue`

B 的快照任务落库后自己会调 `notify.push_summary(...)`，A 不用触发；需要 A 的只有发送通道：

| 模板 | 收件人 | 去重键 | 正文 |
| --- | --- | --- | --- |
| `dorm.list.summary` | 该楼栋 00:00 此刻在班人员 | `dorm:{building_id}:{service_date}:SUMMARY` | 【已汇总】YYYY-MM-DD 当晚晚归申请共 N 人，名单已同步；该时刻起只接受改期与撤销，异动实时更新。 |

- `enqueue` 未实现时该条推送抛 501，worker 会把快照任务打回 `PENDING` 重试；快照写入是幂等的，
  重试不会产生第二份基准，去重键也保证只发一条。
- 只报当夜人数，明细走名单接口，不要把名单塞进消息体。

## 3. 24:00 截止由 A 在申请入口判定，且必须按业务夜传参

B 只提供时刻口径，请勿自己写 `(23, 30)` 或 `hour == 0`：

```python
from app.core.clock import is_summary_passed, summary_moment

# service_date 是这条申请要预约的那一夜，不是「今天」。
if change_kind_is_first_application and is_summary_passed(now, service_date):
    raise ...  # 409/422 由 A 定，文案要说明「今晚申请已截止，可改期或撤销」
```

- `summary_moment(D, tz)` 读配置 `DORM_SUMMARY_AT`（默认 `24:00` = D+1 00:00 = 门禁时段起点）。
- **改期与撤销在该夜 24:00 之后仍然允许**（R07 不变），只有该夜的首次申请被关。
- **不能不传第二个参数**：`is_summary_passed(now)` 取的是 `now` 所属业务夜，16 日 00:05 会算成 15 日夜，
  于是把次夜申请一起关掉。这是需求 ③ 明确不允许的（次日仍可申请）。
- 次夜申请自身的**开放**时刻仍按 R05（该业务日 06:00 起），基线目前这样写死；
  若需求方改成「零点一到即放开次夜」，只需改 R05 一句加 A 入口一处，B 侧无需改动（见 `docs/13`）。
- 已返宿或业务日结束后不得再改（基线「统一日期与边界」第 4 条），这条也在 A 侧。

## 5. 二维码通行（口径 ③④）：B 已交付，A 只需接两个接缝

宿舍门禁 00:00–06:00 的通行情况已经并入阿姨的汇总单与返宿记录，并且**通行本身不推送任何消息**。
A 侧要做的只有两件事，都在预约事务里，不要另开连接：

### 5.1 核验通过后签发二维码

```python
from app.modules.access import service as access

issued = access.issue_pass(
    reservation_id,           # A 的预约 ID（B 只存字符串，不建外键）
    reservation_version,      # 签发时的版本号，改期后旧码据此作废
    {
        "student_id": "stu_synth_0001",
        "building_id": "bldg_a1",
        "gate_id": "gate_a1_north",
        "verification_id": "vs_...",   # A 的身份核验记录 ID
        "planned_return_at": "2026-11-16T00:40:00+08:00",
        "window_start": "2026-11-16T00:10:00+08:00",   # R08：计划时间 ±30 分钟
        "window_end": "2026-11-16T01:10:00+08:00",
        "verified_at": "2026-11-16T00:05:00+08:00",
    },
)
# issued["token"] 是二维码明文，只在签发时返回一次；库里只存 sha256 摘要。
```

- 时段（`window_start/window_end`）**必须由 A 按 R08 算好原样传入**，B 不再猜；缺字段直接 500。
- 同一预约再次签发会自动把旧码置 `REVOKED`（部分唯一索引 `uq_one_active_pass_per_reservation` 保证「一条预约最多一个有效码」）。
- 改期与撤销请调 `access.revoke_passes(reservation_id)`，返回作废条数；旧码再扫只得到 `PASS_REVOKED`。

### 5.2 返宿事实只有 B 能写

A 不要写 `return_records`。扫码核销由 B 的 `POST /api/v1/device/scan` 完成，
成功时在同一条事务里调用 `returns.confirm_return(conn, ...)` 落一条正式记录。
人工补录走 `POST /api/v1/return-records/manual`。

- 一学生一业务夜最多一条（`uq_return_per_night`）：并发扫码、扫码与补录竞争、回执重放都收敛到同一条。
- 因此**名单页的「已通行」只看 B 的记录**：`reservation_status == FULFILLED` 不再被当作已返宿（R10）。

## 7. 联调时请一起验的八条

1. 23:59 首次申请成功 → 名单出现且无异动标记；00:00 该业务夜首次申请被拒。
2. 00:05 不能抢先申请次夜（R05 的开放时刻仍为 06:00）；06:00 开放次夜，不混入前夜名单与汇总。
3. 00:05 改期成功 → 名单该条变【改期】，当班阿姨收到一条 `dorm.reservation.rescheduled`。
4. 撤销成功 → 名单该条变【撤销】且仍在列表里；收到 `dorm.reservation.cancelled`。
5. 00:00 汇总任务跑完 → 阿姨收到一条 `dorm.list.summary`，N 只数当夜非取消预约，不把无码补录行当预约。
6. 23:00 代班生效后 bldg_a2 才可见；失效后 `/buildings/bldg_a2/tonight` 返回 403 `OUT_OF_SCOPE`。
7. 核验通过领码 → 终端 00:40 扫码成功 → 名单该条显示「已通行 00:40」，`已通行 X / 共 N 人` 跟着涨，
   且**阿姨不会收到任何通行推送**；同一码重扫只返回既有记录，不补第二条。
8. 06:00 一到名单自动切次夜；前一晚的码与返宿回「返宿记录」页按 `service_date` 查。

演示时钟用 `POST /api/v1/demo/clock {offset_minutes}`，设置页有「汇总前 23:50 / 推进到 24:00 / 门禁中 00:40」三个按钮。
终端页在 `/terminal`，设备身份下拉选 `dev_synth_a1_01`，明文口令按 `docs/10` 的合成约定派生。
