# 运行手册

本机已验证可用的版本组合，另一台机器请对齐大版本，小版本由锁文件决定。

| 组件 | 版本 | 说明 |
| --- | --- | --- |
| Node.js | 24.16.0 | 前端构建；`node -v` 应为 24.x |
| npm | 11.13.0 | 依赖用 `package-lock.json` 锁定 |
| Python | 3.13.12 | 后端与 worker；Windows 用 `py -3.13` |
| PostgreSQL | 17（容器） | 由 `docker-compose.yml` 启动 |
| Docker Desktop | 29.x，Linux 引擎 | 需要先手动启动 Docker Desktop |

**什么都没装的新机器从下一节开始**；环境已就绪的机器直接跳到「第一次准备」。
除安装步骤外，所有命令都在仓库根目录执行。本机没有 `make` 时直接用本文命令，Makefile 目标与它们等价。

## 零环境新机器：从安装开始（Windows 10/11）

全程约 30–60 分钟，含一次重启；安装需要管理员权限。每步末尾有验证命令，**验证通过再做下一步**。
winget 不可用时用括号里的官网安装包代替，效果相同。安装完都要新开一个终端再验证。

### 1. Git for Windows

PowerShell：

```powershell
winget install --id Git.Git -e --source winget
```

（或官网 <https://git-scm.com/download/win> 下载安装，一路默认。）验证：

```bash
git --version
```

### 2. Python 3.13

PowerShell：

```powershell
winget install --id Python.Python.3.13 -e --source winget
```

（或 <https://www.python.org/downloads/> 下载 3.13.x 安装包，勾选 "Add python.exe to PATH" 与 py launcher。）验证：

```bash
py -3.13 --version
```

### 3. Node.js 24

推荐直接用锁定版本安装包：<https://nodejs.org/dist/v24.16.0/node-v24.16.0-x64.msi>，一路默认。
也可 PowerShell `winget install --id OpenJS.NodeJS.LTS -e --source winget`，装完必须确认大版本是 24.x。验证：

```bash
node -v
npm -v
```

### 4. WSL2 与 Docker Desktop

Docker Desktop 依赖 WSL2，Windows 家庭版也支持。管理员 PowerShell：

```powershell
wsl --install --no-distribution
```

完成后**重启电脑**。若提示虚拟化未开启：任务管理器 → 性能 → CPU，确认「虚拟化：已启用」；未启用需进 BIOS 打开（各品牌按键不同）。

重启后安装 Docker Desktop：PowerShell `winget install --id Docker.DockerDesktop -e --source winget`，或官网 <https://www.docker.com/products/docker-desktop/> 下载安装。首次启动可跳过登录；确认使用 WSL2 引擎（家庭版默认即是）。验证（Docker Desktop 已启动）：

```bash
docker --version
docker compose version
```

### 5. 获取仓库

**仓库目前没有配置远程**，先和 A 约定交付方式，二选一：

- 推荐：两人建一个私有远程（Gitee/GitHub 均可），A 推送后 B 执行 `git clone <仓库地址>`，后续协作也走这里。
- 临时：A 打包源码 zip 发给 B（不含 `.venv`、`node_modules`、`dist`、`.env`），B 解压到任意目录。

然后进入仓库根目录，后续命令都在这里执行：

```bash
cd <仓库根目录>
```

### 6. 安装项目依赖

继续执行下一节「第一次准备」。跑通后 B 的第一批任务见 `双人协作分工.md` S0 阶段：数据库、合成数据、目录、代班。

## 第一次准备

在仓库根目录执行（Git Bash）。前四行可重复运行，不会破坏已有数据；最后一行仅首次执行。

```bash
docker compose up -d postgres
(cd apps/web && npm ci)
(cd apps/api && py -3.13 -m venv .venv)
apps/api/.venv/Scripts/python.exe -m pip install -r apps/api/requirements.lock.txt
cp .env.example .env
cp apps/api/.env.example apps/api/.env
```

PowerShell 用户逐行执行：`cd` 进目录做完再 `cd` 回根目录，`cp` 换成 `Copy-Item`。
两个 `.env` 都是 gitignore，只放本地合成口令，永远不提交。
Compose 已显式设置 `name: jiaowogui`，中文目录不再需要额外配置项目名。根 `.env` 用于可选覆盖 Compose 与演示参数。
`apps/api/.env` 只覆盖后端自身要读的几项；二维码有效期等演示参数在根 `.env`
（`PASS_CODE_SECONDS`、`DORM_SUMMARY_AT` 等，配置见 `app/core/config.py`）。
`docker compose up` 拉取镜像慢或失败时，先检查网络与代理，再考虑在 Docker Desktop 里配置镜像加速。

## 写入合成演示数据

数据库起来后先灌一次演示数据，否则名单、值班与测试都是空的：

```bash
(cd apps/api && .venv/Scripts/python.exe -m app.db.seed --service-date 2026-11-15)
```

`--service-date` 是基准演示夜，双方测试与交接文档都锚在这一夜；不带参数会按真实当天生成值班窗口，
写死 `2026-11-15` 的用例会查不到收件人而失败（详见 `docs/10-演示数据与账号.md`）。
脚本每次都会先清空再写入，可重复执行。

## 每天开工

```bash
# 终端 1：数据库（Docker Desktop 已启动时），仓库根目录
docker compose up -d postgres

# 终端 2：后端，从仓库根目录
cd apps/api
.venv/Scripts/python.exe -m uvicorn app.main:app --reload --port 8000

# 终端 3：前端，从仓库根目录
cd apps/web
npm run dev

# 终端 4：后台任务（园区导出、今晚名单快照都靠它渲染），从仓库根目录
cd apps/api
.venv/Scripts/python.exe -m app.worker.main --once   # 或去掉 --once 常驻轮询
```

浏览器打开 <http://localhost:5173>，点任意合成账号即可进入。后端接口文档在 <http://localhost:8000/docs>。
后端每次重启后演示时钟都回到真实时间，演示前把服务端时钟对齐到基准夜 `2026-11-15`
（命令见 `docs/10-演示数据与账号.md`「基准演示夜」），否则园区端默认区间会往后踩进没有种子数据的夜里。
不起 worker 也能统计查询，但导出任务会一直停在 `PENDING`，下载得到 409 `EXPORT_NOT_READY`；
页面会提示「任务仍在排队」，起一个 `(cd apps/api && .venv/Scripts/python.exe -m app.worker.main --once)` 再点「刷新任务」即可。
门口终端模拟页在 <http://localhost:5173/terminal>（免登录，用设备身份，见 `docs/10` 的设备凭据）：
粘贴学生领到的二维码令牌即可核销，成功后阿姨端「今晚名单」与「返宿记录」都会看到这条通行。

## 交检之前的自检

```bash
(cd apps/api && .venv/Scripts/python.exe -m pytest -q)
(cd apps/web && npm run build)
```

两条都通过才算可以提交。`pytest` 出现 `FAILED` 时先读断言里的状态码，不要直接跳过测试。

## worker

```bash
# 只排空一次到期任务后退出
(cd apps/api && .venv/Scripts/python.exe -m app.worker.main --once)

# 常驻轮询（默认 30 秒一轮），演示时另开一个终端挂着
(cd apps/api && .venv/Scripts/python.exe -m app.worker.main)
```

worker 启动时是唯一允许扫描任务表的进程；API 进程内不启动任何定时器。

通知链路的用法：园区页面「演示投递」或 `POST /api/v1/notification-dispatch` 只入队，
正文里看到的名单、日报、周报和跟进提示都是 worker 消费任务时才渲染入库的，所以入队之后要跑一次
`--once` 才会在「模拟收件箱」里出现。`deliver_now=true` 只是把计划时刻排到当下，仍然要 worker 消费，
不绕过任何校验。

演示时钟的偏移量存在 `apps/api/.demo_clock.json`（已 gitignore，属本地运行态），API 与 worker 读同一份，
所以把时钟推到 24:00 或 06:00 之后，周期任务的到期判断也跟着走，不必重启任何一个进程。
推进方式仍是设置页的「演示时钟」或 `POST /api/v1/demo/clock {offset_minutes}`；把它设回 `0` 即恢复真实时间。
`deliver_now=true` 依旧可用，它只是把计划时刻排到当下，不绕过校验。正式版没有这种偏移，
到期判断改用数据库时间或调度服务系统时间（已登记在 `13-待确认事项.md`）。

## 辅导员报告页

辅导员工作台的「报告」页随时可读，不必等周期任务：`GET /api/v1/reports/daily?service_date=` 出当夜明细，
`GET /api/v1/reports/weekly?service_date=` 出该夜往前七夜的逐夜汇总。默认读前一晚，因为业务夜在 06:00 才结束。
计数口径与投递正文里的日报、周报共用同一份，两处不会出现不同数字。
负责关系还没同步时这两个接口返回 403 `SCOPE_UNRESOLVED`，页面按拒绝显示，不会退化成全校名单；B 的目录落地后即可读。
日报/周报订阅已实现：各自独立开关落 `report_subscriptions` 表，周期投递由 worker 排程（`reports/subscriptions`、`worker/scheduler`），排队后退订会阻止投递；邮件投递时刻按配置与排程触发。

## 整合验收（PowerShell，独立测试库）

不要把测试指向正在演示的开发库。测试会重建合成数据，数据库名必须以 `_test` 结尾。

```powershell
docker compose up -d postgres
docker exec jiaowogui-postgres createdb -U demo jwg_integration_test
$env:JWG_TEST_DATABASE_URL='postgresql+psycopg://demo:demo@localhost:5432/jwg_integration_test'
$env:DATABASE_URL=$env:JWG_TEST_DATABASE_URL
make check
```

库已存在时跳过 `createdb`。Windows 没有 make 时，顺序执行以下等价检查：

```powershell
apps/api/.venv/Scripts/python.exe -m pytest apps/api/tests -q
npm --prefix apps/web run build
apps/api/.venv/Scripts/python.exe contracts/preview.py
Push-Location apps/api
.venv/Scripts/python.exe -m alembic heads
Pop-Location
```

只在未提供 `JWG_TEST_DATABASE_URL` 时明确跳过数据库测试；配置了库之后连接或迁移失败均报错，不能算通过。新通知事件由 worker 消费，预约成功本身不等待投递。实际开发库升级前先备份，确认属于 A 的原迁移历史；B 独立旧库不要直接升级或 stamp，见 docs/07。
