# Git 提交与分支

这一份是必须照做的操作规范。命令都可以直接复制，不用理解 Git 内部原理，只需要记住三条：**提交前先看 `git status`；只在自己分支上写；不要碰已经推给别人看的历史。**

## 名词对照

| 词 | 在这里的意思 |
| --- | --- |
| repository / 仓库 | 整个项目文件夹加上 `.git`，本仓库根目录就是 `交我归/` |
| commit | 一次存档，有唯一编号，记录作者、说明和改了什么 |
| branch / 分支 | 一条平行的开发线，`main` 是主干 |
| HEAD | 你现在所在的位置，正常总是指向某个分支 |
| remote | 另一台机器上的同一份仓库，用来互传提交 |
| merge | 把分支的成果并回主干 |
| conflict / 冲突 | 同一处文件两人都改了，Git 要求人选一个 |

## 每天开工

```bash
git status
git switch main
git log --oneline -5
```

`git status` 应该显示 `nothing to commit, working tree clean`。
如果有上次没提交的改动，先把它提交到该分支或者说明清楚，不要直接改新东西。

## 提交节奏

- 一个功能确认做完 = 一次提交，不要攒一天。
- 中间调试可以反复改工作区，但不要提交半成品。
- 顺手改的小修正，单独一次提交。
- 说明写「为什么这么改」，不要写「改了什么文件」——文件列表 Git 已经知道了。

## 提交信息格式

第一行：`类型(模块): 一句话中文摘要`，控制在 50 字以内。

```
feat(reservation): 允许无限次改期并保留修订历史

预约窗口外仍可改期，符合 R07；改期与扫码竞争时锁定同一归返聚合，
避免出现两次返宿。契约与 409 冲突样例已同步到 contracts/。
```

类型只能用：`feat` 新功能、`fix` 修错、`test` 只加测试、`docs` 只改文档、`refactor` 不改行为的重构、`chore` 工程杂项。
模块用后端模块名或前端角色名，例如 `reservation`、`access`、`student`、`campus`。

## 禁止操作

下面这些会毁掉别人的工作，项目里一律禁止：

| 禁止 | 原因 |
| --- | --- |
| `git push --force` | 会覆盖对方的提交 |
| `git reset --hard` | 会直接丢掉未提交的改动 |
| `git clean -fd` | 会删掉未跟踪文件，包括对方刚写的代码 |
| `git rebase` 已推送的提交 | 改写历史会让对方拉不下来 |
| `git commit --amend` 已推送的提交 | 同上 |
| `git checkout -- .` 一把还原 | 会连同自己的改动一起丢掉 |
| 提交 `.env`、密钥、真实学生数据 | 泄露且删不干净 |
| 提交 `node_modules`、`.venv`、`dist` | 体积大且已由 `.gitignore` 排除 |
| 重写已经应用过的迁移文件 | 对方库里的版本号会对不上 |

不确定时，宁可停下来问，也不要执行以上命令。

## 遇到冲突

```bash
git status
git diff
```

冲突标记是 `<<<<<<<`、`=======`、`>>>>>>>` 三段。处理方式：

1. 打开文件，读两边内容。
2. 保留双方逻辑，删掉三行标记。
3. 跑一遍自检命令。
4. `git add 冲突文件` 然后 `git commit`。

看不懂对方为什么这样写，就停下来问，不要直接删对方的代码。

## 万一改坏了

先保现场，再求助：

```bash
git switch -c backup/broken-state
git log --oneline -10
```

`backup/` 分支只用来留证据。找回某个文件的历史内容用：

```bash
git log --oneline -- 文件路径
git show 提交编号:文件路径
```

不要用 `git reset --hard` 「回到干净状态」。
