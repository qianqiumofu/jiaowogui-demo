# 时间与边界

时间口径最容易让两个人的实现分叉，因此统一走服务端时钟。

## 规则要记牢

- 业务时区固定 `Asia/Shanghai`，数据库存带时区时间戳。
- 晚归门禁时段 `[00:00, 06:00)`，06:00 恢复正常通行。
- `service_date = D` 表示 D 日 06:00 起可申请，对应 D+1 日 00:00—06:00 的那个夜晚；业务日区间 `[D 06:00, D+1 06:00)`。
- 每晚一条预约、一次返宿；预约全部自动通过，不设人工审批队列。
- 只有现场核验要求在预约时间前后 30 分钟内（端点包含）；改期不受原窗口约束。
- 最晚可选返宿时刻＝门禁结束前一个核验窗口（默认 `05:30`＝`06:00`−30 分钟），服务端 `_assert_in_window` 以此为含上界，时钟接口用 `latest_return_at` 下发，学生端下拉只列到这一档。这样「预约时刻 ±30 分钟」的核验窗口不会越过 06:00，06:00 后不再核验、不再签发晚归码（用户 2026-11-19 确认）。
- 二维码自签发起完整有效 300 秒，可越过核验窗口上界；过期必须重新核验，不能刷新续期。
- 06:00 后夜间通行授权结束，终端返回 `NIGHT_ACCESS_ENDED`，即使码在 300 秒内仍未失效；上一行的 05:30 上限已从源头避免在 06:00 后产出这种废码。
- 24:00（业务夜 D 的 D+1 00:00）给宿管汇总**当夜**名单并主动推送人数，同时关闭业务夜 D 的**首次申请**；之后 D 这一夜只允许改期与撤销（R12）。
- 截止判定传的是「预约所属业务夜」，不是墙上钟：`is_summary_passed(now, reservation.service_date)`。16 日 00:05 申请 `service_date=15` 被拒，申请 `service_date=16` 是次夜、不受 15 日那次截止影响（其开放时刻仍按 R05 的 06:00）。
- 超时未返宿、预约后未确认返宿：只记录，不发任何通知，不触发预警。
- 「今晚名单」严格只覆盖 `service_date_of(now)` 那一夜：06:00 一到接口自己翻到次夜，
  前一晚的通行与二维码使用情况到 `GET /return-records?service_date=YYYY-MM-DD` 按业务夜回查，
  名单页不保留跨夜数据、也不因为通行推送任何消息（R18）。
- 返宿记录的 `service_date` 用记录自己的值，不用墙上钟翻页；`PASS_EXPIRED`、`EXPIRED` 这类
  过期态只在扫码时落库或按 `expires_at` 派生，不生成通知任务（R15）。

## 怎么写代码

```python
from app.modules.verification import windows

# 窗口与码寿命只在 verification/windows.py 判定，别处不再写 30 或 300。
state = windows.window_of(res.planned_return_at).state_at(now)   # NOT_OPEN / OPEN / ENDED
code_alive = windows.is_code_live(issued_at, now=now)           # 第 299 秒真，第 300 秒假
gate = windows.pass_state(service_date=res.service_date, issued_at=issued_at, now=now)
```

- 预约响应的 `verification` 块就是 `windows.reservation_view` 的输出，学生端只显示它，不自行比较时刻。

- 前端**只展示**服务端返回的窗口判定结果与剩余秒数，不参与判定。
- 边界一律写显式比较并在测试里覆盖端点值：`00:09:59 / 00:10:00 / 01:10:00 / 01:10:01`，签发后 `299s / 300s`。
- worker 扫描任务用业务时区计算，不允许用 UTC 直接比较小时。
- 演示时用 `POST /api/v1/demo/clock {offset_minutes}` 推进时间，不要 sleep 真实等待。
- 该偏移写在 `DEMO_CLOCK_FILE` 指向的共享文件里，API 与 worker 各自 `build_clock()` 都读到同一份，
  所以「页面显示 23:35」与「24:00 名单任务是否到期」用的是同一个现在；正式部署没有偏移，读真实系统时间。
- `GET /api/v1/demo/clock` 返回 `service_date`（服务端判定的业务夜 D）、`night_window`
  （当夜门禁时段 `[start, end)`，端点带时区）和 `latest_return_at`（最晚可选返宿时刻，默认 05:30）。
  学生端要列举可选返宿时刻时，只能按 `night_window` 起点到 `latest_return_at`（含）生成，不要各自
  `new Date()` 推算跨 06:00 的归属，也不要在前端写死 00:00–06:00 或 05:30；提交后仍以服务端窗口校验为准。
- 下拉档位还要与 `now` 联动：已经过去的时刻不列出，当前一档保留表示「现在就回」；推进演示时钟后重新取一次
  `GET /api/v1/demo/clock`，不把过期档位留在选项里，也不给提交它的机会。
- 演示时钟的偏移是**分钟**粒度，会保留真实时间的秒数：`jump_clock(client, 6)` 得到的是 05:59:13
  而不是 06:00:00。要卡整点边界请显式 `.replace(hour=6, minute=0, second=0, microsecond=0)`，
  别拿 `offset` 的分钟数当整点。

## 必测场景（对应基线「必须共同通过的场景」）

1. 00:40 预约：00:09:59 核验失败，00:10:00 与 01:10:00 成功，01:10:01 失败；窗口外仍可改期。
2. 签发后第 299 秒可用、第 300 秒失效；窗口末尾领码仍完整五分钟。
3. 两设备并发扫码、扫码与补录并发、重复回执：最多一个当夜返宿事件。
4. 超时一小时未确认：只有记录变化，四类角色都收不到通知。
5. 06:00 前后归属切换正确，旧码不获得新一夜通行资格。
6. 23:59:59 首次申请成功、00:00:00 该业务夜首次申请被拒；同一时刻改期与撤销仍成功并实时进名单。
7. 00:00:01 提交**次夜**申请不得被当夜截止误伤；次夜预约不出现在当夜名单与当夜汇总人数里。
