## 需要问学校或后续讨论

- 24:00 作为该业务夜首次申请截止是否为校方口径（现为需求方确认的 Demo 规则，改期与撤销不受限）。
- **次夜申请的开放时刻**：24:00 之后当夜关闭、次夜不受牵连已确认，但次夜是「零点一到就能申请」还是仍按 R05 的 06:00 开放，两条规则目前并存。基线按 R05（06:00）写死，需求方如要 00:00 即开放，改 R05 一句并让 A 在申请入口按次夜放开。
- 预警阈值、重复触发口径、弹窗频控与邮件周期的正式值。
- 日报、周报、24:00 名单的实际投递时刻，以及是否需要按收件人所在时区而非统一业务时区投递。
- 风险提示是否要求辅导员回执确认；当前 Demo 只在正文里说明「演示配置，不是校规」，不采集确认动作。
- 正式版的到期判断应以数据库时间还是应用服务器系统时间为准：Demo 用共享文件里的演示偏移让 API 与 worker
  看到同一个「现在」，正式部署不存在这种偏移，需要换成数据库时间或单一调度服务的系统时间，并约定时钟漂移上限。
- 宿管工号账号是否一律由园区统一注册分发，还是允许楼栋主管分级创建；外包人员离场时的账号停用责任人与时限。
- 统一身份能否给出「学生／教师／外聘」标识，用于自动识别进入哪个工作台（R18）。
- 真实门禁型号与二维码/NFC 能力，扫码回执的证据等级约定。
- **二维码是持有即有效**：Demo 里终端只校验码本身（单次使用、时段、门点绑定），不校验刷卡人是不是学生本人。
  校方若要「人码同源」，需要终端加人脸或校园卡二次确认，这一条会改 R08/R10 的实现口径。
- 核验供应商、精度要求与替代验证路径（定位不准或手机不可用时走人工确认）。
- 临时住宿、例外备案、补录回填与纠错权限。
- 敏感字段与导出范围、数据保留期与校内部署方式。Demo 里的现成口径是：导出只出聚合六列（不含姓名/学号/联系方式）、内容留 7 天、任务行永久留作审计、只有发起人可下载。这四条任一项要改都需要校方给值——尤其「园区不同角色之间是否共享导出」现在是**不共享**。
- 园区统计默认区间的正式口径：2026-11-17 需求方定 Demo 取 **14 夜**（与种子历史等长，首屏人数与晚归夜数必然不等），
  校方若要「近一自然周 / 上一整月 / 自定义」只需改这一个常量，但要同步契约描述、前端提示与那条边界测试，
  否则不同人截图对不上数。
- 闵行片区的正式名称与楼栋归属（现为西一—西五、东一—东四共 9 片区的合成数据）、年级是否按入学年份原值展示。
- 团队工期与演示规模。

## 怎么登记一条新的默认

1. 在 `业务规则基线.md` 的「Demo 工程默认」段落写清楚取值和理由，注明「非校规」。
2. 在代码里做成配置项，不写死在业务判断里。
3. 在 `contracts/openapi.yaml` 暴露需要的枚举或字段。
4. 加一条测试锁住边界值。
5. 提交说明中列出影响到的端点与页面。

**不存在超时未返宿提醒任务**：这条不是默认，而是已确认规则 R15，任何人不得加回。

## 本轮已核定的整合事项

- `users.source` 归一、工号明文仅 Demo；固定管理楼栋 ∪ 有效代班来自 R19 与分工，不再登记成“新账号无排班就没有任何范围”。
- 首次申请仍按 R05 于 06:00 开放，R12 于业务夜的 24:00 截止；00:00–06:00 不提前开放次夜。
- 迁移只支持已验证的空库和 A 原历史，B 的独立旧库需要单独迁入；验证通过不等于所有旧库历史可以混用。
- 缺失功能及工程限制以 docs/16 的代码核对表为准。
